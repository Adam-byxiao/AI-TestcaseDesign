## 2. 维度一：覆盖度 —— 78/100（B）

### 2.1 得分依据

**✅ 优点**

1. **需求覆盖面无缺口**：6 个模块与 PRD §4.1「本次改动范围」的 6 项一一对应，无遗漏、无越界
   （PRD §4.2「不在本次范围」的内容未被错误纳入）。
2. **P0 需求 11/11 全覆盖**，且 P0 用例占 28%（26/94），高于 P0 需求占比 23%，优先级倾斜合理。
3. **覆盖维度有分层**（按标题/预期/数据关键词推断）：

   | 维度 | 条数 | 占比 |
   |---|---:|---:|
   | 正向流程 | 45 | 48% |
   | 反向/校验 | 35 | 37% |
   | 异常/失败 | 22 | 23% |
   | 边界值 | 8 | 9% |

4. **有超出字面需求的推导用例**，体现真正的测试设计而非"需求转写"：
   - `TC-KB-018` 搜索无结果空态（PRD 未提，属错误推测）
   - `TC-AGENT-009` 连续三次点击保存的幂等性（PRD 未提）
   - `TC-AGENT-007` 未保存刷新后内容丢失（PRD 未提）
   - `TC-KB-030` 拖拽非法格式被拒（PRD 只提"支持拖拽"）
5. **关键 P0 点做了深度展开**：`REQ-KB-009`（文件类型与大小限制）有 6 条用例覆盖
   类型白名单、大小临界、超出拒绝等完整等价类。

**❌ 扣分项**

1. **「100% 覆盖率」不可信（-8）**：该 100% 来自 `traceability.json` 的自我申报。
   而 §3 已证明 **19% 的 REQ 引用是错的**，KB 又存在双重生成。
   实际独立覆盖的需求数应低于 47 —— 覆盖率存在**虚高**。
2. **PRD 明确要求但完全未覆盖的路径（-6）**：

   | PRD 位置 | 要求 | 用例覆盖 | 责任判定 |
   |---|---|---|---|
   | §6.1.3 规则 2 | 提示方式参考现有「**保存中**」「**保存失败**」的兜底方案 | **0 条** ❌（仅覆盖"保存成功提示" 4 条） | **用例侧主责**：PRD 显式写明 |

   - 「保存中/保存失败」是 PRD §6.1.3 的**显式验收项**（原文：「提示方式参考现有"保存中""保存失败"的兜底方案」），
     用例却只测了成功路径，属真实缺口。
   - 「长结果折叠」在 PRD 中**提及但未定义**（§6.4 标题为「文字测试界面优化与长结果折叠」，
     配图说明「长工具结果折叠」，但规则表 3 条规则与 3 条验收要点**都没有它**）。
     这是 **PRD 欠定义**导致的用例缺失，用例侧只能算次要责任 —— 不可测未定义之物。
     **该缺口更应反馈给 PRD 作者补充规则**，而非单方面归咎于用例生成。

3. **边界值仅 9%（-4）**：PRD 的数值约束已覆盖（20 字 / 1 MB），但其余边界未测 ——
   列表 0 条、超长提示词、页签数量上限、名称仅空格、超长列表滚动等均无。
4. **SCENE（1.11）与 TOOL（1.50）用例/需求比偏低（-4）**：这两个模块在 PRD §6.2/§6.3 中
   规则密集（工具字段可编辑范围、动态展示机制、场景草稿与发布链路），但展开不足。
5. **无网络异常类用例（-2）**：`超时`、`断网` 命中 0 条。虽 PRD 未明确要求，
   但对"配置保存 + 文档上传 + RAG 解析回调"这类强依赖后端的链路，属合理应补充项。

### 2.2 结论

覆盖面「广而欠深」，且**因重复生成与映射错误导致覆盖率虚高**。
若剔除 KB 的重复部分，有效用例约 60–70 条，对 47 条需求而言属于"够用但不宽裕"。

**关于扣分的一个诚实说明**：本维度原本可评更高，但有两处不宜归咎于用例生成 ——
「长结果折叠」在 PRD 中只出现在改动范围表与 §6.4 标题/配图，**正文规则与验收要点均未定义**，
属**PRD 欠定义**。评测已就此降低扣分（-8 → -6），并在建议中标注"应先回补 PRD 规则"。
> 这提示一个流程改进点：**当 PRD 提及某功能但未给出规则时，生成器应显式告警"需求不可测"**，
> 而不是静默跳过或凭空编造 —— 本次它选择了静默跳过。

## 3. 维度二：准确度 —— 62/100（C）

### 3.1 得分依据

**✅ 优点**

1. **REQ 引用无悬空**：102 次引用全部指向真实存在的需求（0 个不存在的 ID），
   说明"需求指纹/编号锚定"机制在**存在性**层面有效。
2. **关键量化事实全部与 PRD 一致**（逐项核对原文）：

   | PRD 事实 | 用例体现 | 判定 |
   |---|---|---|
   | 三页签顺序：主提示词 → 工具 → 业务场景 | `TC-AGENT-001` 预期「从左至右依次为…」 | ✅ |
   | 首次进入默认展示主提示词 | `TC-AGENT-001/002` | ✅ |
   | 文档名称 20 字上限 + 计数 | `TC-KB-007` 测 19/20/21 三态 | ✅ 超预期 |
   | 单文件 ≤1 MB | `TC-KB-008/025/026` 测 1048575/1048576/1048577 | ✅ 超预期 |
   | 类型白名单 txt/docx/xlsx | `TC-KB-009/027/028` | ✅ |
   | 删除二次确认文案含"文档及知识片段" | `TC-KB-012/041` | ✅ |
   | 排序与得分按接口实际、前端不伪造 | `TC-KHTEST-007` | ✅ |
   | 前端无绑定关系选择/解绑入口 | `TC-SCENE-002` | ✅ |

   其中 `1048577`（1 MB + 1 byte）这类精确边界值是**主动构造**的，而非照抄 PRD，说明模型理解到位。
3. **无金额/数值类臆造**：PRD 未涉及金额，用例也未编造。

**❌ 扣分项**

1. **REQ 引用语义错配 18/94 = 19%（-14）**

   集中在两个模块：**KB 33%、AGENT 24%**。

   确凿错误（关键词零重合）：
   ```
   TC-KB-031「启用开关切换为开启状态生效」  → 引用 REQ-KB-011『选择后显示文件名称』
   TC-KB-032「启用开关切换为关闭状态生效」  → 引用 REQ-KB-011『选择后显示文件名称』
   ```
   正确目标应是 `REQ-KB-012`『启用开关控制是否参与当前 Agent 知识检索』。

   `validator.py` 只校验 REQ **是否存在**，不校验**语义是否对得上**，因此全部放行。

2. **臆造 PRD 未定义的 UI 行为（-10）**

   | 用例 | 臆造内容 | PRD 实际 |
   |---|---|---|
   | `TC-AGENT-012/013/014/015` | 弹窗含**保存 / 放弃 / 取消三选项**及各自完整行为分支 | §6.1.3 仅写「**弹窗提醒**用户当前内容尚未保存」，**未定义任何选项** |

   由这一处臆造派生出 **4 条用例、约 30 个步骤**，占 AGENT 模块 24%。
   即使这三选项在业界常见，也属**把设计决策当既定事实**，评审会误导研发。

3. **臆造 PRD 未提及的场景（-6）**

   | 用例 | 内容 | PRD |
   |---|---|---|
   | `TC-AGENT-007` | 未保存时刷新页面内容丢失 | 「刷新」出现 **0 次** |
   | `TC-TEST-008` | 刷新后收起状态保持 | 「刷新」出现 **0 次** |

4. **143 个自拟标识符，PRD 依据为 0（-5）**

   用例引用了 143 个 `data-testid` / 元素 id，**PRD 全文 `data-testid` 出现 0 次**。
   这些标识符可视为"实现建议"，但用例以**事实语气**书写，且：

   - **同一页面两套路由**：`/knowledge/list`（批 1）vs `/agent/knowledge-base`（批 2）—— **直接矛盾**
   - **同一元素两个名字**：搜索框 `kb-search` vs `kb-search-input`；
     上传窗口 `upload-dialog` vs `kb-upload-modal`；名称输入框 `field-name` vs `kb-upload-name-input`

5. **11 个不可定位的 target（-3）**

   ```
   network-save-draft          tab-tool.active           panel-text-test.collapsed
   network-text-test           tab-scene.active          panel-text-test.right
   btn-save-all-draft.enabled  tab-main-prompt.active    panel-text-test.expanded-narrow
   dialog-unsaved-tab-switch.visible                    dialog-unsaved-test-block.visible
   ```

   这些是"状态路径"或"网络请求计数器"，**不是 DOM 元素**，无法映射为 Playwright 选择器。
   写成 `check` 动作后，下游代码生成必然失败。

### 3.2 结论

**"表面事实准确、深层语义失真"**：能被逐字对照的 PRD 事实全部正确，
但一旦涉及 PRD 未明确的部分（弹窗选项、标识符命名、路由），就从"忠实转写"滑向"自由设计"，
且**未标注哪些是推断**。19% 的 REQ 错配是硬伤。

## 4. 维度三：测试用例结构合理性 —— 74/100（B）

### 4.1 得分依据

**✅ 优点**

1. **字段完整度极高**（12 个字段，97–100% 填充）：

   | 字段 | 有值 | 占比 |

2. **动作枚举规范且可机读**（10 种动作，550 个步骤）：
   ```
   click 134 | expectVisible 118 | goto 86 | expectText 71 | fill 52
   check 47 | waitFor 16 | selectOption 15 | reload 9 | expectUrl 2
   ```
   操作类与断言类动作分离清晰，**具备直接生成自动化脚本的结构基础**。
3. **粒度合理**：步骤中位数 6（范围 3–15），预期中位数 2（范围 1–3），无过粗或过细极端。
4. **可独立执行**：90%（85/94）的用例首步为 `goto`，前置条件 100% 填写，具备独立运行性。
5. **设计方法分布健康**，无明显单一方法依赖：

   | 方法 | 条数 | 占比 |
   |---|---:|---:|
   | 场景法 | 45 | 48% |

   且方法选择与用例性质匹配（状态迁移用于解析状态机、边界值用于 20 字/1 MB、判定表用于弹窗分支）。

6. **编号规范**：`TC-<模块>-<序号>` 全模块连续无断号，便于溯源与维护。

**❌ 扣分项**

1. **`check` 动作 100% 语义误用（-12，最严重）**

   动作契约中 `check` = 勾选复选框（对应 Playwright `page.check()`）。
   实测 **47 个 `check` 步骤中，0 个是勾选复选框，47 个全部当作断言使用**：

   ```
   check  主提示词页签激活态 (tab-main-prompt.active)
   check  保存接口请求次数 (network-save-draft)
   check  文字测试容器状态 (panel-text-test.collapsed)
   check  召回结果不包含已停用文档的片段 (data-testid=hit-results)
   ```

   下游按契约生成 `page.check('tab-main-prompt.active')` → **运行时必然报错**。
   这等于 **47 个"伪断言"**，掩盖了真实断言覆盖不足。

2. **target 标识符存在 4 种并存写法（-6）**

   | 写法 | 数量 | 占比 | 主要模块 |
   |---|---:|---:|---|
   | `元素名 (data-testid=xxx)` | 265 | 48.2% | TOOL、KB |
   | `元素名 (bare-id)` | 152 | 27.6% | AGENT、TEST、KHTEST |
   | 纯中文描述（无 id） | 119 | 21.6% | SCENE |
   | 路径 `/xxx` | 14 | 2.5% | — |

   **同一批产物内 4 种约定并存**，且按模块分化（SCENE 100% 纯中文、AGENT 100% 裸 id、
   TOOL/KB 100% data-testid）。下游必须写 4 套解析分支。

3. **5 条用例无任何断言动作（-4）**：
   `TC-AGENT-011`、`TC-AGENT-013`、`TC-AGENT-017`、`TC-KHTEST-008`、`TC-SCENE-006`
   —— 只有操作步骤，无法判定通过/失败。

4. **断言密度偏低（-2）**：真实断言 191 / 操作 359 = **0.53**（理想约 0.8–1.0）。
5. **`expected` 与 `steps` 无显式关联（-2）**：预期结果集中写在 `expected` 数组，
   依赖**位置顺序**隐式对应步骤，而非每步显式断言。步骤调整后对应关系易错位。

### 4.2 结论

**结构骨架优秀、语义细节有硬伤**。字段规范、动作枚举化、粒度合理，已具备自动化生成条件；
但 `check` 动作的全量误用与 4 套标识符约定，会使自动化落地时"结构可用、执行报错"。

## 5. 维度四：测试用例重复性 —— 55/100（D）

### 5.1 得分依据

**✅ 优点（自动化去重机制有效）**

1. **严格签名重复 = 0**：`validator.py` 的 `case_signature()`（模块+步骤+预期）未发现重复。
2. **标题完全相同/包含 = 0**：无两条用例标题雷同。
3. **步骤序列完全相同的仅 3 组**，且均为**合法的参数化变体**：
   - `TC-KB-025` × `TC-KB-027`（1 MB 临界值 vs 合法类型，测点不同）
   - `TC-KB-031` × `TC-KB-032`（启用开 / 关，双向必测）
   - `TC-KHTEST-001` × `TC-KHTEST-004`（未启用 vs 解析失败，条件不同）
4. **同一 REQ 内语义重叠仅 2 对**，亦属合法分支（开/关、两种失败条件）。

**❌ 扣分项（严重）**

1. **KB 模块被生成两遍并拼接，11 组语义重复（-30，本次评测最严重发现）**

   KB 的 42 条可清晰切分为两个独立批次：

   | 批次 | 用例区间 | 条数 | 覆盖的需求 |
   |---|---|---:|---|
   | 批 1 | `TC-KB-001` ~ `TC-KB-014` | 14 | REQ-KB-001 ~ 016（**完整一遍**） |
   | 批 2 | `TC-KB-015` ~ `TC-KB-042` | 28 | REQ-KB-001 ~ 016（**又完整一遍**） |

   **KB 的 16 个需求 100% 被覆盖 ≥2 次**，其中 `REQ-KB-009` 被覆盖 **6 次**。

   语义重复对（11 组，占 KB 的 **52%**）：

   | 批 1 | 批 2 | 相同行为 |
   |---|---|---|
   | TC-KB-001 | TC-KB-015 | 知识库入口可见/跳转 |
   | TC-KB-002 | TC-KB-016 | 列表展示完整字段 |
   | TC-KB-003 | TC-KB-017 | 按名称搜索过滤 |
   | TC-KB-005 | TC-KB-020 | 重置清空搜索与筛选 |
   | TC-KB-006 | TC-KB-021 | 上传窗口字段完整 |
   | TC-KB-007 | TC-KB-023 | 文档名称 20 字边界 |
   | TC-KB-008 | TC-KB-025 | 文件大小 1 MB 边界 |
   | TC-KB-009 | TC-KB-027 | 文件类型白名单 |
   | TC-KB-010 | TC-KB-029 | 点击/拖拽上传 |
   | TC-KB-012 | TC-KB-033 | 删除二次确认弹窗 |
   | TC-KB-013 | TC-KB-037 | 解析失败点击更新 |

2. **为什么自动门禁没拦住（关键洞察）**

   `case_signature()` 基于**文本**（模块+步骤+预期）。两批对同一行为给出的是
   **不同的路由和不同的 testid**：

   ```
   批1  TC-KB-001  goto 后台首页   →  /knowledge/list
   批2  TC-KB-015  goto 智能体配置页 (data-testid=page-agent-config)  →  /agent/config
   ```

   文本不同 → 签名不同 → **判为非重复**。

   > **这是本次评测最重要的方法论结论：**
   > **基于文本签名的去重，无法识别「命名不同但语义相同」的跨批次重复。**
   > 现有 C-007 门禁对此类重复**结构性失效**（完整失效链条见 §7.2，已修复）。

3. **其他模块也存在重复覆盖（-8）**：

   | 模块 | 需求数 | 被 ≥2 条用例覆盖 |
   |---|---:|---:|
   | **KB** | 16 | **16（100%）** |
   | TEST | 4 | 4（100%） |
   | AGENT | 8 | 6（75%） |
   | TOOL | 6 | 3（50%） |
   | KHTEST | 4 | 1（25%） |
   | SCENE | 9 | 2（22%） |

4. **净影响**：94 条用例中，**去重后约 60–70 条为独立行为**，
   即 **约 30% 的用例量是重复膨胀**。这同时虚高了覆盖率（§2）并浪费约 1/3 生成成本。

### 5.2 结论

**自动化去重"看起来有效"，实际对跨批次重复完全失效。**
KB 模块 52% 冗余是本次评测最严重的质量问题，且它会连带污染覆盖度与准确度的评估结果。

## 7. 根因分析：为什么会出现 52% 重复 + 19% 错配

> **本节已于 2026-10-12 修订**。初版报告把根因推断为「模块级重试的合并语义（替换 vs 追加）」，
> 那是**错的**。经查运行事件日志（`.prd2tc-workspace/events/c653dc92-*.jsonl`）后已更正为下述
> **批次切分未被机器约束**，并已完成修复与回归防护（见 §7.4）。

### 7.1 权威证据：事件日志

事件日志是该运行的完整留痕，直接给出批次结构：

```
176 个事件，类型分布：
  module_started 6 | batch_started 7 | module_finished 6 | module_progress 18 | heartbeat 125

按模块汇总 batch_started：{AGENT: 1, KB: 2, KHTEST: 1, SCENE: 1, TEST: 1, TOOL: 1}
```

KB 的时间线：

```
02:27:56  KB module_started · batch=0/2      ← 恰好 2 批
02:27:57  KB batch_started  · batch=1/1
02:31:46  KB batch_started  · batch=2/1
02:35:40  KB module_finished · state=succeeded · tokens=109454
```

**关键**：KB 只有 2 批，且**没有任何拆批（split）事件** —— 直接排除「截断自愈拆批导致重复」
与「检查点重复生成」两种假设。

### 7.2 真正的机制：批次是「提示级隔离」而非「契约级隔离」

KB 有 16 条需求 → 按批量切为 2 批。但实测两批的**需求覆盖集合完全相同**：

| | 覆盖的 REQ | 交集 |
|---|---|---|
| 批 1（`TC-KB-001~014`，14 条） | REQ-KB-001 ~ 016（**全部 16 条**） | **16 / 16** |
| 批 2（`TC-KB-015~042`，28 条） | REQ-KB-001 ~ 016（**全部 16 条**） | |

**两批本该互斥（各 8 条），实际各自覆盖了全部 16 条需求** → 16 条需求各被独立覆盖两次。

旁证（说明两批确为**独立生成**，而非同一批被复制）：

| 语义元素 | 批 1 | 批 2 |
|---|---|---|
| 列表页路由 | `/knowledge/list` | `/agent/knowledge-base` |
| 搜索框 | `kb-search` | `kb-search-input` |
| 新增按钮 | `kb-add-btn` | `kb-add-doc-btn` |
| 上传窗口 | `upload-dialog` | `kb-upload-modal` |
| 名称输入框 | `field-name` | `kb-upload-name-input` |
| 列表页容器 | — | `page-kb-list` |

两批 42 / 37 个 testid 中**仅 1 个重合**；且批 2 的需求引用相对批 1 **整体错位一格**
（如实测「启用开关」批1 → `REQ-KB-012` ✅ / 批2 → `REQ-KB-011` ❌，
而 `REQ-KB-011` 实为「选择后显示文件名称」）—— 与 §3 的 19% 错配同源。

失效链条（四道防线全部落空）：

| # | 位置 | 应有作用 | 实际 |
|---|---|---|---|
| 1 | `stages.py` 批次提示 | 「本批仅覆盖以下 N 条需求，不要生成与其它批重复的用例」 | **只是自然语言建议**，模型未遵守（`module_context` 检索到的 PRD 原文含整个 KB 小节，模型按所见全量生成） |
| 2 | 门禁 `allowed` | 拦截越界引用 | 只校验**模块码** `{module}`，批1 引用批2 的需求**不会报错** |
| 3 | `all_cases.extend()` | 汇总各批 | **裸叠加**，无任何跨批去重 |
| 4 | `renumber()` + `case_signature()` | 去重/可追溯 | `renumber()` 顺序重编号**抹掉批次边界**；`case_signature()` 基于文本比较，两批对同一元素用了不同 testid（`kb-search` vs `kb-search-input`）→ **判为非重复，放行出厂** |

### 7.3 完美相关性：只有多批的模块才出现重复

| 模块 | 批次数 | 需求 | 用例 | 被 ≥2 条覆盖的需求 |
|---|---:|---:|---:|---:|
| AGENT | 1 | 8 | 17 | 6/8 |
| **KB** | **2** | **16** | **42** | **16/16** ← 唯一多批 |
| KHTEST | 1 | 4 | 8 | 1/4 |
| SCENE | 1 | 9 | 10 | 2/9 |
| TEST | 1 | 4 | 8 | 4/4 |
| TOOL | 1 | 6 | 9 | 3/6 |

6 个模块中**只有 KB 被切成 2 批，也只有 KB 出现 100% 重复覆盖**。
其余 5 个模块均为 1 批，其 ≥2 条覆盖来自合法的正/反分支（如「启用→开」与「启用→关」）。

> **这是本次评测最关键的结论**：重复不是模型的随机失误，而是
> **「模块内多批」这一结构性路径的必然产物** —— 只要一个模块的需求数超过批量，
> 就会重复生成，且现有四道防线一个都拦不住。

### 7.4 已完成的修复

**修复 1（结构性，主）：批次范围成为机器强约束**

门禁在通用校验之外增加**批次级需求范围检查**，越界立即成为门禁错误并回灌给模型，
由既有重试机制要求其收窄到本批：

```python
batch_req_ids = frozenset(str(r.get("id")) for r in batch)   # 本批拥有的需求

def gate(value, _allowed=allowed, _bids=batch_req_ids):
    errs = ...check_cases_text(value, _allowed, ...)
    # 越界检查**独立于**其它门禁错误：若写成「仅在无其它错误时才查」，
    # 一旦同时存在 C-007 类错误，越界就会被掩盖而放行（实测踩到此坑）。
    out_of_scope = sorted({...} - _bids)
    if out_of_scope:
        errs.append(f"越界引用：本批只负责 {sorted(_bids)}，但用例引用了 {out_of_scope}。…")
    return errs
```

**修复 2（兜底）：跨批去重 `dedup_cross_batch()`**

即使模型仍越界（或 `use_gate=False`），也会按「需求归属批次」保留唯一供例：
某需求的供例批次 = 拥有它的批次；若拥有批未产出则取最早产出者。
每个批次只保留「其引用的需求全部由本批供例」的用例，混合引用则裁剪引用。
由规则可知供例批必然产出过该需求，故**不会产生覆盖缺口**。
去重发生时会通过 `reporter` 显式提示，不静默改产物。

**在真实 KB 数据上的效果**（穷举所有可能的批次切分）：

| 批次切分 | 保留 | 丢弃（重复） | 识别冲突 | 覆盖缺口 |
|---|---:|---:|---:|---:|
| [9,7] | 24 | 18 | 16 | 无 |
| [10,6] | 23 | 19 | 16 | 无 |
| [12,4] | 20 | 22 | 16 | 无 |
| [15,1] | 16 | 26 | 16 | 无 |

即：**能消除 43%–62% 的重复用例，且不丢任何需求覆盖**。

**修复 3：回归防护（`tests/test_cross_batch_dedup.py`，11 个测试）**

其中 `test_model_ignoring_batch_scope_does_not_produce_cross_batch_duplicates`
用「伪造一个无视批次范围的模型」直接复现 c653dc92 的失败模式。
**变异测试证明防护有效**：分别破坏两处修复，对应测试立即失败 ——

```
① 绕过跨批去重（等价修复前的裸 extend）  → 2 failed ✅ 被捕获
② 去掉门禁的批次范围校验                → 2 failed ✅ 被捕获
```

## 9. 评测方法与可复现性

**评测方式**：以 PRD 原文为唯一事实基准，对 94 条用例做
① 逐字段量化统计、② 逐条人工核对（全文通读 6 个模块）、③ 自动化语义比对（2-gram 重合度）、
④ **运行事件日志（`events/*.jsonl`）与检查点、产物三方交叉验证**。

**关键判据**：

| 维度 | 判据 |
|---|---|
| 覆盖度 | `traceability.json` + PRD §4.1/§6 逐条对照 + 维度关键词分类 |
| 准确度 | REQ 引用存在性 + 「最佳匹配需求 ≠ 被引用需求」检测 + PRD 原文事实核对 |
| 结构 | 12 字段填充率 + 动作枚举分布 + 断言/操作比 + target 形态分类 |
| 重复性 | `case_signature()` 严格签名 + 标题 Jaccard 相似度 + **事件日志批次结构 + 批次需求集合重叠度** |
| 可读性 | 长度统计 + 标点率 + 空洞表述词典 + 粘连句检测 |

> **方法论教训**：初版报告仅凭产物文件推断根因，得出了错误的机制（检查点重复）。
> 纠正它的是**运行事件日志** —— 它直接证明「KB 恰好 2 批、无拆批事件」。
> 结论：**产物只能证明"重复存在"，事件日志才能证明"重复如何产生"**；
> 排查流水线缺陷必须查事件留痕，而非只看最终文件。
