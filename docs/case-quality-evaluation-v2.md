### 3.3 ⚠️ 本轮发现的新严重问题：契约校验器对实际 target 格式失明

**这是工具缺陷，不是产物缺陷 —— 但它使「97% 合规」失去了门禁保障。**

#### 证据链

**(1) 提示词规定的格式**（`04-case-constraints.md:8`、`00-testing-principles.md:53`）：

> `target` 用「页面元素中文名 **(data-testid)**」格式

**(2) 校验器正则**（`prototype.py:624`）—— 与提示词格式一致：

```python
_IDENT_IN_TARGET_RE = re.compile(r"\((?:data-testid=)?([A-Za-z_][\w.\-]*)\)\s*$")
```

**(3) 但模型实际使用的格式** —— 620 个标注 target 的分布：

| 标注形式 | 数量 | 正则是否匹配 |
|---|---:|---|
| `class=` | 328 | ❌ |
| `id=` | 195 | ❌ |
| `page=` | 83 | ❌ |
| `text=` | 13 | ❌ |
| 裸标识符 | 1 | ✅ |

**620 个标注中正则只匹配到 1 个** → `validate_targets` 恒返 0 问题 → **门禁形同虚设**。

#### 为什么模型换用了新格式

因为我注入的 UI 契约（`render_ui_spec`）是这样呈现的：

```
- 页签：main（主提示词）、tools（工具）、skills（业务场景）
- 可用 id 锚点（20 个）：app、chat、count、docFile、docName、...
- 可用 class 锚点：account、actions、avatar、...
- ⚠ 该原型是单页应用…：`goto` 请使用下列页面键（如 `page=config`）
```

契约里**明确出现了 `page=config` 这种写法**，并分别列了「id 锚点」「class 锚点」。
模型据此**自行归纳**出 `(id=xxx)` / `(class=xxx)` / `(page=xxx)` / `(text=xxx)` 标注法。

**客观评价：模型的格式比提示词规定的更好** —— 它携带了「种类」信息，
比裸的 `(data-testid)` 更利于机器解析。问题在于**校验器不认识它**。

#### 由此暴露的两层缺陷

| 层 | 缺陷 | 后果 |
|---|---|---|
| **格式层** | 提示词要求 `(data-testid)`，注入契约暗示 `(key=value)`，两者冲突 | 模型自行发明格式，校验器失效 |
| **语义层** | 即使匹配成功，校验也只查「值是否存在」，**不查「种类是否匹配」** | `id=tools` 会被放行 —— 因为 `tools` 作为**页签键**存在于契约中 |

**(4) 语义层缺陷的实证**：19 处不合契约的 target 中，**17 处**是同一类问题 ——
`id=tools`(9)、`id=skills`(5)、`id=main`(3)。

契约**明确标注**这三个是「页签」，**不存在**任何 `kind=id` 的 anchor 名为 `tools`：

```
页签：main（主提示词）、tools（工具）、skills（业务场景）      ← 是页签键
可用 id 锚点（20 个）：app、chat、count、docFile、docName…      ← 不含 tools/skills/main
```

即模型把**页签键当成了元素 id**。这类「跨命名空间误用」本应被门禁拦下，
却因格式失明 + 只查值不查种类而全部放行。

剩余 2 处为：`text=测试草稿名称`（临时造的数据名，非契约文案）、
`(DevTools Network)`（裸标识符，网络断言的自然语言表述）。

**结论**：97% 的合规率来自 `ui-spec` 被注入 system 前缀（模型「照抄」了真值），
**而非门禁强制**。门禁当前的**真实拦截能力为 0**。

## 9. 评测方法与证据

本报告全部结论均来自**逐条枚举**，而非关键词计数：

- 覆盖度：22 个子节 × 关键词逐节核验；46 条需求对照追溯矩阵
- 准确度：620 个 target **逐条**按「种类 + 值」比对契约；
  19 个专用术语在全部产物中检索
- 结构：12 字段逐字段统计；121 条映射关系核对
- 重复性：5 组同签名用例**逐组人工判定**（区分「合法等价类」与「真重复」）
- 可读性：23 次 `check` **逐条**归类

数据脚本：
- 摄取与需求/用例汇总 → `$TEMP/eval_collect.py`
- 准确度与动作语义 → `$TEMP/eval_accuracy.py`
- 契约合规（正确解析）→ `$TEMP/eval_contract.py`
- 追溯/重复/结构 → `$TEMP/eval_final.py`

### 方法论教训（本次新增）

1. **「门禁报告 0 问题」不等于「产物合规」** —— 必须独立复核门禁本身的覆盖能力。
   本轮若只信 `validate_targets` 的 0 问题，会把 19 处不合契约 target 漏掉。
2. **同步骤签名 ≠ 重复** —— 等价类与边界值本就「同流程、不同数据」。
   判定重复必须结合 `testData` 与设计意图，否则会误伤正确的测试设计。
3. **对比评测必须确认基准一致** —— v1 的 PRD 是 AI 扩写版（17,855 字节），
   v2 是原件（3,993 字符）。两轮对比的「提升」中，一部分来自**输入本身变干净**，
   而非模型能力提升。本轮已尽量以**同一份原件**为基准。
