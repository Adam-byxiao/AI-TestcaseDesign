# 门禁失败处理手册

本文说明 prd2tc 在需求分析、测试方案和用例生成阶段遇到门禁失败时，开发者和使用者应该如何判断、修复和继续运行。

## 先理解门禁是什么

门禁是对模型输出的程序化检查，不是对 PRD 原文的“格式评分”。模型输出即使语句通顺，只要缺少必需章节、引用了不存在的 REQ、JSON 字段不符合契约，流水线也会停止。停止是保护措施，避免不可信内容进入后续阶段。

默认流程如下：

1. 调用模型生成当前阶段内容。
2. 程序执行当前阶段门禁。
3. 失败时把完整错误清单反馈给模型，并按 `maxGateRetries` 重试（CLI 默认 2 次）。
4. 重试后仍失败，运行状态为 `failed`，错误写入运行详情和 `run-manifest.json`，不会自动进入下一阶段。
5. 修复输入或模型配置后，使用恢复/重新生成；不要把失败产物直接当作正式产物。

Stub 模式用于离线验证界面、审批、检查点和文件落盘，不代表真实模型质量。Stub 产物必须在工作台中显示为“Stub 离线验收”。

## 三类输入的责任边界

| 问题类型 | 通常责任方 | 首选处理 |
| --- | --- | --- |
| PRD 没有业务规则、指标或异常定义 | 需求输入 | 补充 PRD，保存为新版本，再重新分析 |
| 模型报告缺少“业务规则”等章节 | 模型输出/Prompt | 先重试或编辑分析草稿；不要为了迎合报告结构随意编造 PRD 内容 |
| 用例引用不存在的 REQ、字段或 action 非法 | 模型输出/数据契约 | 修正结构化需求或用例草稿，重新生成失败模块 |
| API 超时、鉴权失败、连接拒绝 | 环境/Provider | 检查会话、地址、Key、超时和网络后恢复 |
| 质量门禁阈值不适合当前产品 | 配置/Profile | 调整 profile 或覆盖阈值，并在评审记录中说明原因 |

判断原则：只有当 PRD 本身缺少事实时才修改 PRD；如果事实已经在 PRD 中，而报告没有抽取出来，应优先修复模型输出、Prompt 或人工草稿。

## 阶段 1：需求分析门禁

### 必备章节缺失

典型错误：

```text
缺少必备章节「业务规则」
缺少必备章节「非功能需求」
缺少必备章节「风险与疑点」
```

这些章节是**分析报告的输出契约**，不要求 PRD 必须拥有同名标题。处理顺序：

1. 打开失败运行的分析报告，确认模型是否完全省略章节。
2. 如果 PRD 中有相应事实，点击“恢复/重新生成”，并确认使用真实模型而不是 Stub。
3. 如果模型连续重试仍失败，可在分析阶段保存草稿，补齐章节。没有事实的章节应明确写“未定义/待确认”，并在“风险与疑点”中记录，不要编造指标。
4. 如果 PRD 确实没有业务规则、非功能指标或风险信息，先编辑 PRD 保存新版本，再点击“重新分析”。

### 需求遗漏或虚构

典型错误：

```text
需求分析遗漏需求点 REQ-PROD-002（PRD 中存在但报告未覆盖）
需求分析出现 PRD 中不存在的需求点 REQ-AUTH-999
```

处理方式：

- “遗漏”：检查 PRD 的需求表、标题和编号是否清晰；若事实存在，重新分析或手工补齐对应需求。
- “虚构”：删除报告中的虚构 REQ；如果是模型临时编号，必须标记为“自动编号”，并保留 `sourceId`/原文引用。
- 修改结构化需求时只修改 `requirements.json` 草稿，不会覆盖 PRD 原文；确认事实变化时才另存 PRD 新版本。

## 阶段 2：测试方案门禁

测试方案必须包含范围、策略、优先级、风险、环境、准入/准出和用例量目标等章节。出现“缺少必备章节”时，先把它当作方案输出不完整处理：

1. 用当前分析报告重新生成方案。
2. 仍失败时编辑方案 Markdown，补充章节和可执行内容。
3. 没有依据的内容写成“待确认”，并把问题放入风险/开放项；不要为了过门禁填充虚假数字。
4. 保存并批准方案后，才允许进入用例阶段。

## 阶段 3：用例与追踪门禁

常见错误及动作：

| 错误关键词 | 含义 | 处理 |
| --- | --- | --- |
| `JSON 解析失败` | 模型没有返回合法数组 | 重试；检查是否混入 Markdown 说明或代码围栏外文本 |
| `id 重复` | 多条用例使用同一 TC 编号 | 修改编号或重新生成失败模块 |
| `module/priority/action 非法` | 字段不在版本化枚举中 | 使用当前 Schema 支持的值，不要自定义 selector/action |
| `requirement 格式非法` | REQ 格式不符合约定 | 引用 `requirements.json` 中真实 ID |
| `引用了不存在的需求` | TC → REQ 断链 | 先修正 REQ ID，再保存/批准用例 |
| `P0 需求没有 active 用例覆盖` | 质量门禁发现关键需求缺口 | 为该 REQ 增加 active 用例，或调整需求优先级并记录理由 |
| `重复映射需求` | 同一映射关系被重复提交 | 删除重复引用，保留明确的覆盖关系 |

模块级失败只需要重试失败模块；已经成功并写入检查点的模块不会重复调用模型。若修改了 PRD、Prompt、模型或 Schema 指纹，检查点不再安全复用，应重新生成或使用 `--force` 明确放弃旧检查点。

## API/Provider 类错误

这类错误通常不会产生“缺少章节”，而会在运行错误中出现 `401/403`、超时、连接拒绝或模型响应为空。处理顺序：

1. 在“模型配置”重新保存 Provider、模型、API Base 和临时 Key。
2. Ollama 检查本地服务和模型名；OpenAI/Anthropic 检查 Key 权限和地址。
3. 适当增加超时或降低并发，不要通过开启 Stub 冒充真实生成成功。
4. 使用“恢复”继续失败阶段；确认运行详情显示“真实模型”。

API Key 只保存在服务进程内存中，不应出现在 manifest、事件日志、截图或错误报告中。

## CLI 操作参考

```bash
# 查看门禁失败的退出码和错误清单
prd2tc generate --prd PRD.md --out output

# 增加模型反馈重试次数
prd2tc generate --prd PRD.md --max-gate-retries 3

# 仅在人工接受风险并需要继续流程时使用；结果必须标记为告警
prd2tc generate --prd PRD.md --allow-gate-fail

# 恢复输入、Prompt、模型、示例和 Schema 指纹一致的检查点
prd2tc generate --prd PRD.md --out output --resume

# 明确放弃旧检查点（例如 PRD 已变更）
prd2tc generate --prd PRD.md --out output --force
```

`--allow-gate-fail` 和 `--no-gate` 不适合正式产物验收。前者会把风险带入后续阶段，后者会关闭机器校验；它们只适合调试 Prompt 或定位问题。

## 工作台操作参考

1. 在运行详情查看失败阶段、完整错误清单、质量门禁和事件时间线。
2. 若是模型输出问题，点击“恢复”；若只某个模块失败，在模块列表点击“重试”。
3. 若是需求事实变化，进入 PRD 页面保存新版本，再显式点击“重新分析”。
4. 阶段显示“等待审阅”后，先保存草稿，再批准或驳回；驳回时填写具体原因。
5. 只有阶段批准且门禁通过后，才把 JSON/Markdown 下载给下游执行器。

## 提交问题时应附带的信息

请提供以下信息，不要提供 API Key：

- `runId`、阶段和运行模式（真实模型/Stub）。
- 错误清单原文。
- PRD 版本、内容哈希和是否刚编辑过。
- Provider、模型、脱敏后的 API Base。
- `run-manifest.json` 中对应阶段的 gate、重试次数和状态。
- 相关 `requirements.json`、方案或用例片段（去除敏感业务数据）。
