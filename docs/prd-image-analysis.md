# PRD 图片识别与分析：设计说明

> 编制日期：2026-10-12 | 实现：`src/prd2tc/images.py`
> 实测样例：`prd-7d537530d799.md`（8 处图片引用）+ 用户提供的 `图片和附件/`（8 张图）

---

## 0. 问题：图片里的设计真值此前完全不可达

PRD 下载为 Markdown 后，**图片通常不会内联**，而是作为同目录/子目录下的独立文件一起下载
（例如 `prd.md` + `prd.assets/` 或 `图片和附件/`）。实测现场：

```
prd-7d537530d799.md           8 处图片引用，全部为 https://feishu.cn/file/... （需鉴权）
工作区 .prd2tc-workspace/      本地图片 0 张
loader.load_prd()              只 read_text，完全不解析图片引用
```

**后果**：PRD 里最关键的 UI 事实（线框图、字段布局、**弹窗按钮**、状态枚举、
以及用红框标注的「本次改动点」）从未参与生成。这与
[prototype-truth-gap.md](prototype-truth-gap.md) 记录的是同一类缺陷 ——
**设计真值不可达 → 模型只能编造**。

最典型的代价：PRD §6.1.3 只写了「弹窗提醒」四个字，
用例因此编出「保存/放弃/取消」三选项弹窗（4 条用例、约 30 个步骤）。
而拿到设计图后可见，通知栏原文是：

> 停止编辑后**自动保存**草稿，**切换内容时会保留修改**。自动保存不等于发布，点击"发布"才更新线上配置。 [查看未保存修改]

**根本不存在阻塞式三选项弹窗**。图里还有 PRD 正文没有的事实：
行号/字数计数器（`16 行 · 235 字`）、状态标签（`与已发布内容一致`、`全部草稿已保存 · 初始示例`）、
`支持 Markdown · Ctrl/⌘+F 查找`，以及「宽屏并排展开 / 窄屏右侧抽屉」的布局说明。

## 1. 能力总览

| 阶段 | 能力 |
|---|---|
| **发现** | 解析 Markdown `![](...)` 与 HTML `<img>`；记录顺序、图注(alt)、**所在小节**、引用处上下文 |
| **关联** | 在 PRD 同级与约定子目录中匹配本地图片；三阶段**全局唯一分配**，并给出匹配置信方式 |
| **分析** | 调用**视觉模型**把图转成结构化 UI 事实：`kind / summary / annotated / uiElements / fields / states / texts / layout / flows / notes` |
| **缓存** | 键 = `sha256(图片) + 模型 + 提示词版本` → 可复现、不重复计费 |
| **注入** | 作为「**图片推断**」证据注入阶段 1（需求抽取）与阶段 3（用例生成）system 前缀 |
| **留痕** | 契约落盘 `analysis/image-spec.json`；摘要入 `run-manifest.json`；`imageSpecHash` 入 `configHash` |
| **降级** | 缺图 / 远程取不到 / 模型不支持视觉 / 图片损坏 → **只告警不中断** |

零第三方依赖（`urllib` / `base64` / `hashlib`），图片类型按**魔数**嗅探。

---

## 2. 关键设计决策

### 2.1 关联用「最长公共子串」，不用「包含」

图注通常很长，文件名很短，且**互不包含**：

| PRD 图注 (alt) | 实际文件名 | 包含关系 | 最长公共子串 |
|---|---|---|---|
| 业务场景：新增、删除与带行号的内容编辑 | `业务场景编辑.png` | ❌ 互不包含 | **4**（业务场景） |
| 内嵌文字测试：配置与测试并排、长工具结果折叠 | `文字测试界面.png` | ❌ 互不包含 | **4**（文字测试） |
| 知识库配置：文档列表及添加入口 | `知识库配置与添加.png` | ❌ 互不包含 | **5**（知识库配置） |
| 知识命中测试：片段、文档来源及评分 | `知识库命中测试.png` | ❌ 互不包含 | **4**（知识命中测试） |

实测：**「包含」判定只能关联 3/8（38%），最长公共子串可达 8/8（100%）**。

阈值 `MIN_ALT_OVERLAP = 3`：CJK 下 3 字已具区分度
（「知识库」可区分「知识库配置」与「知识库命中测试」，而「配置」2 字太泛会被拒）。

### 2.2 三阶段全局唯一分配

```
阶段 0  explicit   target 就是存在的相对路径            （最高置信）
阶段 1  filename   与 target 的 basename 同名/同形
阶段 2  alt        按最长公共子串评分贪心，每文件只用一次
阶段 3  order      仅当「剩余引用数 == 剩余文件数」时顺序兜底（低置信，显式标记）
```

**为什么必须唯一**：若不做全局分配，两条图注相似时可能双双落到同一张图，
导致证据张冠李戴（把 A 页面的字段当成 B 页面的）。

**为什么 `order` 要慎用**：实测 PRD 的图序与目录内文件名排序**并不一致**
（`智能体配置整体.jpeg` 排在第 5 位，但它对应第 1 处引用），
因此只在数量相等时兜底，且标记 `match="order"` 供人工复核。

### 2.3 图片结论标记为「推断」，不冒充 PRD 明文

渲染时会显式声明：

```
## PRD 图片证据（**来自图片的视觉识别，属推断结论**；与 PRD 明文冲突时以明文为准，
并在用例中标注 `[推断]`）
- 共 8 处图片引用，成功识别 6 张；未识别部分不得凭空补全。
```

这与修复策略中的「支柱 E：诚实标注」一致 —— 图片是**证据**，不是**契约**。
评审者必须能一眼区分「PRD 说的」与「模型从图里看出来的」。

### 2.4 不信任文件扩展名

`read_image()` 按**魔数**判定类型，扩展名仅用于错误提示。
否则改名为 `.png` 的文本文件会被当作有效图片送进视觉模型，浪费调用且污染证据。

## 3. 用法

```bash
# 图片与 PRD 同目录/约定子目录（<stem>.assets/、_files/、images/ 等）→ 自动探测
prd2tc generate --prd prd.md

# 目录名不常规时显式指定（可重复）
prd2tc generate --prd prd.md --images-dir "D:\work\...\图片和附件"

# 允许下载远程图片（飞书等需鉴权链接多半取不到，默认关闭）
prd2tc generate --prd prd.md --fetch-images

# 跳过图片识别（默认开启）
prd2tc generate --prd prd.md --no-images
```

产物：

```
<out>/<product>/<version>/analysis/image-spec.json     # 完整证据（含 refs 关联方式与 warnings）
<out>/<product>/<version>/analysis/.image-cache/       # 按 sha256+模型+提示词版本 缓存
<out>/<product>/<version>/run-manifest.json            # 含 imageSpecHash
```

```
① 发现 8 处图片引用，全部附带小节定位
   #1 智能体配置整体：页签布局及默认收起的测试入口      小节 6.1.1
   #2 工具配置：调用说明及参数填写规则               小节 6.2.1
   #3 业务场景：新增、删除与带行号的内容编辑           小节 6.3.1
   #4 内嵌文字测试：配置与测试并排、长工具结果折叠        小节 6.4
   #5 知识库配置：文档列表及添加入口                小节 6.5.1
   #6 添加文档知识：名称填写、文件上传及保存窗口         小节 6.5.2
   #7 知识命中测试：片段、文档来源及评分             小节 6.5.4
   #8 RAG接口清单：业务标注参考                   小节 6.5.6

② 关联（--images-dir 图片和附件）          8/8 = 100%，全部 match=alt，唯一无重复
③ 读取（严格魔数校验）                     8/8 可读（4 PNG + 4 JPEG）

```

**未做视觉识别时也产出可用产物**（如 stub 模式），并明确告警：

```json

 "warnings": ["已定位 8 张图片，但未做视觉识别（stub 模式）；请配置支持图片输入的模型后重跑以获取图片证据"]}
```

## 5. 回归防护

`tests/test_images.py` —— **42 个测试**，6 项变异测试**全部被捕获**：

| 变异 | 捕获 |
|---|---|
| ① 关联退回「包含」判定（复现 3/8 的真实坑） | ✅ 4 项失败 |
| ② 读取信任扩展名（改名文本冒充图片） | ✅ |
| ③ 去重分配失效（一文件被多引用占用） | ✅ |
| ④ 缓存不校验提示词版本 | ✅ |
| ⑤ 渲染不声明「属推断」 | ✅ |
| ⑥ 显式路径在候选池判空后处理 | ✅ |

**开发中被测试抓出的 4 个真实缺陷**（已修）：

1. **显式相对路径失效** —— 候选池为空时提前 `return`，导致「图片就在 PRD 旁边但目录名不常规」被漏掉；
2. **缓存命中崩溃** —— 缓存体刻意排除了 `index`，但 `ImageInsight.index` 是必填位置参数，
   改为从**当前引用**取 `index/source/alt/section`（缓存按图片内容寻址，同一图在不同文档里序号可能不同）；
3. **`None` 被转成字符串 `"None"`** —— 污染 `texts`；改为丢弃 `None/bool/容器`；
4. **扩展名绕过魔数校验** —— 见 §2.4。

**另修一处设计缺陷**：`find_local` 曾与 `resolve_refs` **重复实现**评分逻辑，
导致「改了一处、测试仍全绿」的假安全感（变异测试 ① 因此未被捕获）。
现改为单一实现（`find_local` 委托 `resolve_refs`）。

## 6. 已知边界

| 边界 | 说明 |
|---|---|
| **需鉴权的远程图** | 飞书 `feishu.cn/file/...` 需登录，`--fetch-images` 通常也取不到；须依赖本地下载的图片 |
| **视觉模型能力** | 需 Provider 支持图片输入（多模态）。不支持时会告警并跳过，不影响生成 |
| **单图上限 8MB** | base64 后约放大 1.33 倍，已接近多数 Provider 请求上限 |
| **图片结论需复核** | 模型可能误读图；已通过「标注为推断 + 保留 `notes` 不确定项」降低风险，但不能替代人工评审 |
| **`order` 兜底置信低** | 目录排序与 PRD 图序不保证一致，`match="order"` 应人工复核 |
| **未做** | OCR 精读小字、图表数值抽取、图片与需求的多对多关联 |
