# 用例质量缺陷：生态根因分析与修复策略

> 编制日期：2026-10-12 | 依据：[case-quality-evaluation.md](case-quality-evaluation.md) 的五维评测
> 分析对象：运行 `c653dc92`（47 需求 / 94 用例 / 6 模块），MiniMax-M3
> 数据来源：`prompts/*.md`、`src/prd2tc/{schema,validator,stages}.py`、运行产物与事件日志

## 0. 摘要：所有低分项共享同一个模式

五个低分项（准确度 62、结构 74、可读性 78，以及已修复的重复性 55、覆盖度 78）
**不是五个独立问题**，而是同一个结构性模式的五种表现：

> **契约（prompt 约束 + schema 词表 + 门禁）与实际可被机器校验/可被输入满足的能力之间，存在信息落差。**
>
> 软约束只写在自然语言里 → 模型可自由偏离 → 门禁不校验 → 缺陷直达用户。

| 低分项 | 表层现象 | 生态根因（本报告新增） | 性质 |
|---|---|---|---|
| 准确度 · REQ 错配 19% | 需求引用错位 | **需求 ID 被重编号，87% 相对模型原始编号偏移** | 锚点不稳定 |
| 准确度 · 臆造交互 | 弹窗三选项 | **无「PRD 未明确处须标注推断」契约** | 契约缺失 |
| 准确度 · 143 自拟标识符 | 4 种 target 写法 | **契约强制 `data-testid`，但输入 0 个（原型亦无该属性）；且示例与约束矛盾** | ✅ 已修复（原型契约接入） |
| 结构 · `check` 100% 误用 | 47 个伪断言 | **动作词表缺 4 类能力（状态23/上传9/计数5/反向4 = 87% 可归因）** | 能力缺口 |
| 结构 · 3 条无判定依据 | 只有操作步骤 | **契约只约束 `expected` 文本，不约束 `steps` 含断言动作** | 契约缺失 |
| 可读性 · `0点91` | 中文数字表小数 | **只规定了金额格式，未规定小数/标点书写** | 契约缺失 |
| 可读性 · 预期歧义 | 一条预期含相反结果 | **无「一用例一分支」约束** | 契约缺失 |

**这个模式已在「跨批重复」上被验证**：把批次范围从自然语言建议升级为门禁强约束后，
重复率从 52% 降至 0（见评测报告 §7.4）。**同样的方法可迁移到上述每一项。**

## 1. 准确度 62（C）的三个根因

### 1.1 REQ 引用错配 19% ← 需求 ID 被重编号，锚点漂移

**这是本次分析最重要的新发现。**

`analysis/requirements.json` 的实测统计：

```
explicit=True       : 0 / 47     ← PRD 中没有任何显式 REQ-* 编号
idSource=generated  : 47 / 47
有 sourceId 的需求  : 47
偏移 != 0 的比例    : 41 / 47 = 87%
偏移分布            : {+1: 35, 0: 6, -2: 2, -4: 1, -6: 1, -7: 1, -14: 1}
```

KB 模块的逐条对照（最终 ID vs 模型原始 ID）：

| 最终 ID | sourceId（模型原始编号） | 偏移 | 需求标题 |
|---|---|---|---|
| REQ-KB-010 | REQ-KB-009 | **+1** | 支持点击选择与拖拽上传 |
| **REQ-KB-011** | **REQ-KB-010** | **+1** | **选择后显示文件名称** |
| **REQ-KB-012** | **REQ-KB-011** | **+1** | **启用开关控制是否参与当前 Agent 知识检索** |
| REQ-KB-013 | REQ-KB-012 | **+1** | 删除需二次确认，确认后移除文档及片段 |

**机制**（`stages.py:498-519`）：

```python
# 顺序化编号：显式保留原号；生成项按模块内顺序 001 起
n = counters.get(module, 0) + 1
candidate = f"REQ-{module}-{n:03d}"
while candidate in assigned:      # ← 跳过已被显式占用的号，导致与模型视图错位
    n += 1
    candidate = f"REQ-{module}-{n:03d}"
item["id"] = candidate            # ← 模型原始 model_id 被丢弃
item["idSource"] = "generated"
```

该函数**丢弃了模型在阶段 1 给出的 `model_id`**，改为按文档顺序重编号。
而阶段 3 拿到的是**最终 ID + PRD 原文（原文中没有任何 ID）**，
模型必须自行把「行为」映射到「ID」—— 它依据自己阶段的编号直觉推断，于是系统性 off-by-one。

**与观测精确吻合**：批 2 把「启用开关」映射到 `REQ-KB-011`，
而 `REQ-KB-011` 的语义是「选择后显示文件名称」。
真值应是 `REQ-KB-012`；模型的原始编号里「启用开关」正是 `REQ-KB-011`。
**这不是模型幻觉，而是它用了被系统丢弃的那套编号。**

**为什么门禁没拦住**：`validator.py` 只校验 REQ **是否存在**（`REQ_RE` 匹配 + 是否在本模块集合内），
不校验「用例内容与被引用需求的语义是否对得上」。18 处错配因此全部放行。

> **结论：需求 ID 不是一个「锚定事实」，而是一个「重编号产物」。**
> 任何依赖 ID 稳定性的映射（traceability、增量比对、用例修订）都会受此影响。

### 1.2 弹窗三选项 ← 无「推断标注」契约

PRD §6.1.3 规则 1 原文：**「如存在未保存修改，弹窗提醒用户当前内容尚未保存」**
—— 只说"弹窗提醒"，**未定义任何选项**。

用例 `TC-AGENT-012/013/014/015` 却生成了完整的三选项分支（保存 / 放弃 / 取消）
及其各自行为，并以**既定事实**语气书写，派生 4 条用例、约 30 个步骤（占 AGENT 模块 24%）。

**生态原因**：`prompts/00`、`03`、`04` 全文**没有任何**「PRD 未明确处如何处理」的规定。
模型面对信息缺口时，默认行为是**用领域常识补全**（三选项确属常见设计），
而非标注为不确定。提示词里唯一相关的话是 `04 §A.5`「禁止模糊步骤」，与推断无关。

**同源问题**：PRD §6.4 标题提到「长结果折叠」但正文无规则 —— 那次模型选择了**静默跳过**（0 条用例），
与弹窗的**臆造补全**是两个相反的坏处理。**同一缺口，两种坏结果。**

> 说明：模型在信息缺口前缺少统一处置策略，行为在「编造」与「忽略」之间摇摆。

### 1.3 143 个自拟标识符 ← 契约要求了输入无法提供的事实

**证据链**：

1. **契约强制**（两处）：
   - `prompts/00-testing-principles.md:53`：「target 用「页面元素中文名 (data-testid)」格式」
   - `prompts/04-case-constraints.md:8`：「`target` 用「页面元素中文名 (data-testid)」格式」
2. **输入无法提供**：
   - PRD 中 `data-testid` 出现 **0 次**
   - PRD §7 引用的原型 `养老Agent后台-prototype-测试内嵌版.html`（48,847 字节）**不在仓库**
   - pipeline **没有任何附件/原型传递通道**（`llm.py` 只把 URL 响应当错误处理，不喂给模型）
3. **必然编造**：模型被要求填一个只能来自原型的字段 → 143 个标识符全部自拟
4. **示例与约束自相矛盾**（决定性旁证）：

   | 位置 | 内容 |
   |---|---|
   | `prompts/03-test-cases.md:18`（自称「格式唯一标准」） | `{"action":"fill","target":"手机号输入框",...}` ← **无 testid** |
   | `prompts/04-case-constraints.md:8`（硬约束） | 必须 `元素名 (data-testid)` |

   模型面对矛盾只好按模块各选一种，实测：

   | target 写法 | 数量 | 占比 | 主要模块 |
   |---|---:|---:|---|
   | `元素名 (data-testid=xxx)`（合规） | 265 | 48% | KB(212)、TOOL(53) |
   | `元素名 (bare-id)` | 152 | 28% | AGENT、TEST、KHTEST |
   | 纯中文元素名 | 119 | 22% | SCENE（100%） |
   | 路径 `/xxx` | 14 | 3% | — |

   **SCENE 100% 采用纯中文（跟示例）、TOOL/KB 100% 采用 data-testid（跟约束）** —— 完美对应矛盾双方。

5. **门禁不校验格式**：`validator.py:177-178` 仅 `if not s.get("target")` 判非空，
   **四种写法自由共存**，无任何拦截。

6. **✅ 2026-10-12 更新：原型已获取，判决完成**

   原型 `养老Agent后台-prototype-测试内嵌版.html` 已到手并解析（见
   [prototype-truth-gap.md](prototype-truth-gap.md)）。逐项判决结果：

   | 项 | 真值 |
   |---|---|
   | `data-testid` | **0 个**（证实「输入侧不存在」） |
   | 真实锚点 | **91 个**（20 个 `id` + 70 个 `class`） |
   | URL 路由 | **不存在**（单页应用，`go(p){page=p;render()}`） |
   | 143 个自拟标识符 | **0 个真实**（100% 编造） |
   | 7 种 URL 路径 | **0 个真实** |
   | 「未保存修改」弹窗 | **只有 1 个「关闭」按钮**（证实用例三选项是臆造） |

   → **决策 A2-a（供给）成立且已实现**：`--attach` 解析原型为 UI 契约，
   注入阶段 3 并作为门禁校验依据。详见下方支柱 A2。

> **结论：契约要求了一个输入侧不存在、且无供给通道的事实。**
> 后果不止"名字难看"——两条矛盾路由（`/knowledge/list` vs `/agent/knowledge-base`）
> 与两套命名（`kb-search` vs `kb-search-input`）正是由此而来，并直接放大了跨批重复。

## 2. 结构合理性 74（B）的两个根因

### 2.1 `check` 100% 语义误用 ← 动作词表缺 4 类能力（**85% 可归因于能力缺口**）

`check` 在生态中**没有任何语义定义**：

| 位置 | 内容 |
|---|---|
| `schema.py:9-12` | 仅一个字符串集合 `{... "check", ...}` |
| `prompts/04:8` | 仅枚举动作名，无解释 |
| `prompts/00:53` | 只讲 target 格式，不讲动作语义 |
| `prompts/03:18` | 示例只用 `goto/fill/click/expectUrl` |

模型只能从英文名猜测 → 而 47 次使用中**0 次**是真正的复选框勾选。

**逐条枚举全部 47 个 `check`**（下表为人工可核对的完整分类，非关键词近似）：

| 类别 | 数量 | 现有词表能否表达 | 实例 |
|---|---:|---|---|
| ③ 元素状态 / 位置 | **23** | ❌ **缺 `expectState`** | `主提示词页签激活态 (tab-main-prompt.active)`、`文字测试容器状态 (panel-text-test.collapsed)`、`工具列表位于左侧` |
| ① 拖拽上传文件 | **9** | ❌ **缺 `upload`/`dragAndDrop`** | `拖拽入 1048575 字节 txt 文件 (data-testid=field-dropzone)` |
| ② 网络请求计数 | **5** | ❌ **缺 `expectCount`** | `保存接口请求次数 (network-save-draft)`、`测试接口请求次数 (network-text-test)` |
| ④ 排他 / 反向断言 | **4** | ❌ **缺 `expectNotVisible`** | `工具详情区无完整JSON编辑框`、`工具列表仅含工具项-天气预报` |
| ⑤ 本应 `click`/`hover` | **4** | ✅ 有动作但选错 | `发起整体命中测试`、`hover 该行查看片段明细入口` |
| ⑥ 本应 `expectVisible`/`expectText` | **2** | ✅ 有动作但选错 | `文字测试图标 (test-icon)`、`召回结果包含该文档的片段` |
| **复选框勾选（唯一正确语义）** | **0** | — | — |

> **41/47（87%）的误用源于词表能力缺口**，仅 6 条（13%）是选错已有动作。

**这不是模型乱来，而是它在填补词表空洞**：
用例需要断言「页签是否激活」「容器是否收起」「接口被调用几次」「拖拽是否被接受」，
而 `expectVisible/expectText/expectUrl` **一个都表达不了**；`check` 是剩下唯一听起来像"验证"的词。
更讽刺的是：**PRD 明确要求「支持点击选择与拖拽上传」（REQ-KB-010），
而词表里没有拖拽/上传动作** —— 模型无法正确表达一个 PRD 显式要求的功能。

> 方法论注记：本表由**逐条枚举**得出。此前用关键词近似统计曾误得「元素状态 21、反向断言 7」，
> 差异源于关键词表不完备（如「位于左侧」「仅含」未被识别）。**量化结论必须以逐条枚举为准。**

### 2.2 无判定依据的用例 ← 契约只约束 `expected` 文本

**5 条用例不含任何 `expect*` 断言动作**（逐条动作序列已核对）：

| 用例 | 动作序列 | 可判定性 |
|---|---|---|
| `TC-AGENT-011` | `goto, click, check, check` | ⚠️ 仅 2 个误用的 `check` |
| `TC-AGENT-017` | `goto, click, check, check` | ⚠️ 仅 2 个误用的 `check` |
| `TC-SCENE-006` | `click×6, fill×2` | ❌ **纯操作，完全无判定依据** |
| `TC-AGENT-013` | `… waitFor, check, check` | ⚠️ 有 `waitFor`（非断言） |
| `TC-KHTEST-008` | `… waitFor ×2` | ⚠️ 有 `waitFor`（非断言） |

> 严格说：**3 条完全无判定依据**（`TC-AGENT-011`、`TC-AGENT-017`、`TC-SCENE-006`），
> 另 2 条靠 `waitFor` 的"超时即失败"勉强可判定 —— 但 `waitFor` 是**同步动作**而非断言，
> 不表达期望值，不应计入断言覆盖。

`prompts/04 §A.3`「预期可断言」约束的是 **`expected` 字段的内容**（长度、可观测对象），
**没有一条**约束「`steps` 中必须至少包含一个 `expect*` 动作」。
`validator.py` 也只校验 `steps` 非空与 `action ∈ ACTIONS`。

→ 用例可以只有 `goto/fill/click` 而没有任何判定依据，**无法判定通过/失败**，却完全合规。

## 3. 可读性 78（B）的两个根因

### 3.1 `0点91` / 标点缺失 ← 只规定了金额格式

`prompts/04 §A.3` 唯一涉及数字书写的规定是**金额**：
「金额给精确值（¥ 千分位、2 位小数，如 ¥4,727.05）」。

**没有**关于小数（`0.91`）、中文标点、多子句分隔的规定。实测：

| 现象 | 实测 |
|---|---|
| 「数字+点+数字」形式（`0点91`、`0点73`） | 2 处 |
| 规范小数点（`0.91`） | **0 处** |
| 预期中使用中文标点的比例 | 45/175 = **26%** |
| 无标点且 >30 字的粘连句 | 5 处（3%） |

其中 `TC-KHTEST-007` 的 `0点91` 属**技术文档不专业书写**；
粘连句如「第二条排序等于2且得分等于0点73排序与得分均与接口返回完全一致前端未做二次调整」
（40 字，零标点，含 4 个子句）。

> 提示词对可读性的约束是**间接的**（只要求"超过 8 字符""写明可观测对象"），
> 因此模型在"满足门禁"与"人类可读"之间只优化了前者。

### 3.2 `TC-KB-012` 一条预期融合两个相反结果 ← 无一用例一分支约束

```
TC-KB-012  expected[2] = 「取消后文档行保留确认后文档行从列表移除」
```

该用例的 steps 确实**同时测了两条路径**（先点取消验证保留，再点确认验证移除），
于是把两个**相反**的判定结果压进同一条 `expected`。

**生态原因**：提示词有「[必须] 独立：不依赖其他用例的执行顺序」（`00 §4`），
但**没有**「一个用例只覆盖一个场景分支」或「一条 `expected` 只描述一个可判定结果」的约束。
`validator` 也不检查 `expected` 项之间的语义互斥。

> 后果不只是可读性：**自动化执行时无法据此生成断言** —— 若先取消后确认，
> 「行保留」在前、「行移除」在后，两条预期天然冲突，脚本无法判定中间态。

## 4. 生态全景：缺陷分布在哪些层

```
输入层   PRD 无 REQ-* 编号（0/47 显式）、无 data-testid（0 次）
         PRD 提及「长结果折叠」但无规则（欠定义）
         原型 HTML 有真实锚点 91 个，但**此前无通道进入生成**（现已由 --attach 打通）
             ↑ 上游欠定义 + 真值可达但未接入
─────────────────────────────────────────────────────────────
契约层   prompts/03 示例（无 testid） ⚔ prompts/04 约束（必须 testid）  ← 自相矛盾
         动作词表缺 4 类能力（状态/计数/上传/反向断言）
         无「推断标注」契约、无「一用例一分支」契约、无「数字/标点书写」契约
             ↑ 软约束只存在于自然语言，无机器表达
─────────────────────────────────────────────────────────────
转换层   _assign_requirement_ids 丢弃模型原始 ID，重编号致 87% 偏移
         renumber() 重编号抹掉批次边界
             ↑ 把「稳定锚点」变成了「派生值」
─────────────────────────────────────────────────────────────
校验层   validator 只查 REQ 存在性（不查语义）、target 非空（不查格式）
         action ∈ ACTIONS（不查语义）、steps 非空（不查是否含断言）
         C-007 只做批内去重（跨批结构失效）
         原型契约校验（新增，仅在有 --attach 时生效）
             ↑ 门禁的检查项远少于 prompt 的约束项
─────────────────────────────────────────────────────────────
汇聚层   all_cases.extend() 裸叠加（跨批重复）              ← 已修复
─────────────────────────────────────────────────────────────
```

**核心失衡**：**契约层的约束项 ≫ 校验层的检查项**。
凡是「只在 prompt 里说过、门禁没查」的要求，实测全部失守：

| prompt 说了 | 门禁查了吗 | 实测结果 |
|---|---|---|
| target 用 `元素名 (data-testid)` 格式 | ❌（现由原型契约校验部分覆盖） | 52% 不合规；有原型时 100% 可拦 |
| 动作取自动作枚举 | ✅（仅成员性） | 100% 成员合法但语义误用 |
| requirement 必须真实存在 | ✅（存在性） | 存在性 100%，语义 19% 错配 |
| 不要重复用例 | ⚠️（仅批内） | 跨批 52% 重复 |
| 预期可断言 | ⚠️（仅长度） | 3 条完全无判定依据 |
| 禁止臆造 | ❌ | 弹窗三选项凭空生成；143 个标识符全编造 |

## 5. 修复策略：五大支柱

### 支柱 A：能力补全（Capability）—— 缺什么就补什么

针对 §2.1（87% 可归因）与 §1.3。

**A1. 动作词表补全 + 语义表**（最高杠杆，成本最低）

```python
# schema.py —— 单一事实源，prompt 与 validator 共用
```

### 支柱 B：契约一致（Consistency）—— 消除自相矛盾
**B1. 示例与约束对齐**：`prompts/03` 的「格式唯一标准」示例必须与 `prompts/04` 的约束一字不差。
（当前矛盾直接造成 SCENE 与 TOOL/KB 的写法分裂。）

**B2. 单一事实源**：动作语义表、target 格式、ID 规则都放 `schema.py`，
prompt 与 validator 共同引用，避免再次漂移（这与 `DESIGN_METHODS` 已有做法一致）。

**B3. 补三类缺失契约**：
- 「PRD 未明确处：必须标注 `[推断]` 并降为 P2，或声明「需求欠定义，需补充 PRD」」→ 修 §1.2
- 「一个用例只覆盖一个场景分支；一条 `expected` 只描述一个可判定结果」→ 修 §3.2
- 「小数用 `0.91`；多子句用中文顿号/逗号分隔；禁止无标点长句」→ 修 §3.1

### 支柱 C：锚定（Anchoring）—— 禁止关键标识漂移

**C1. 需求 ID 锚定**（针对 §1.1，19% 错配的根因）

三选一，推荐 C1-c：

| 方案 | 做法 | 评价 |
|---|---|---|
| C1-a | **不再重编号**，保留阶段 1 模型原始 ID | 改动最小，但失去"人类友好的顺序号" |
| C1-b | 重编号，但**把 `sourceId` 一并传给阶段 3** | 双视图，模型可对照；但增 token 且要求模型理解两套号 |
| **C1-c** | **ID 绑定不可变锚点**：`sourceRefs`（chunkId+start/end）或 `fingerprint` 随 ID 一起传给阶段 3，门禁校验「用例引用的 REQ 的 fingerprint 与其内容主题一致」 | 最稳，可抵御后续任何重编号 |

**同时必做 C1-d：门禁增加 REQ 语义校验**
```python
# validator.py 新增：用例关键词 ∩ 需求(标题+描述+AC)关键词 的下限断言
if overlap_ratio < THRESHOLD:
    errors.append(f"{at} 引用的 {rid}『{title}』与用例内容关键词重合度过低，疑似映射错误")
```
这能直接拦住 18 处错配（含 2 处零重合的确凿错误）。

### 支柱 D：机器强校验（Enforcement）—— 每条软约束都要有门禁

**原则：prompt 里出现的每一条「必须/禁止」，都必须在 `validator.py` 有对应检查项。**
否则它只是建议（实测全部失守，见 §4 表）。

新增门禁项（按 ROI 排序）：

| 门禁项 | 拦住的缺陷 | 成本 |
|---|---|---|
| REQ 引用语义校验 | 19% 错配 | 低 |
| target 格式校验（正则） | 52% 格式不合规 | 极低 |
| 每用例 ≥1 个 `expect*` 断言动作 | 3 条无判定依据 | 极低 |
| `check` 仅允许复选框类 target | 47 个伪断言 | 低 |
| `expected` 互斥结果检测（保留/移除 等词对） | 预期歧义 | 低 |
| 小数/标点规范（`\d+点\d+` 报错） | `0点91` | 极低 |
| 跨批去重 | 52% 重复 | **已完成** |

### 支柱 E：诚实标注（Honesty）—— 欠定义必须显式化

针对 §1.2 与「长结果折叠」漏测：

**E1. 需求欠定义检测**：阶段 1 分析时，若某条规则只有标题/配图而无正文规则，
应产出 `underdefined=True` 标记，并在 traceability 中体现为「不可测」而非静默计入覆盖。

**E2. 推断可视化**：所有 `[推断]` 标记的用例/字段，在 Excel/XMind 导出与 Markdown 评审稿中
**显著标色**，让评审者一眼看到「哪些是 PRD 说的、哪些是模型补的」。这是产品级信任机制。

**E3. 覆盖率诚实化**：`traceability.json` 区分
`covered_by_prd` / `covered_by_inference` / `underdefined` / `uncovered` 四态，
不再用单一 100% 掩盖问题。

## 8. 一句话总结

> **这套流水线的模型能力不是瓶颈，"契约与校验的落差"才是。**
> 凡是只写在 prompt 里的要求，实测都会失守；
> 凡是升级为门禁强校验的，实测都能守住（跨批去重已验证 52% → 0）。
>
> 因此策略不是"把 prompt 写得更严厉"，而是：
> **补全能力（缺的动作/字段）→ 统一契约（消除矛盾）→ 锚定标识（禁止漂移）→ 机器校验（每条软约束配一个硬门禁）→ 诚实标注（欠定义不掩盖）。**
