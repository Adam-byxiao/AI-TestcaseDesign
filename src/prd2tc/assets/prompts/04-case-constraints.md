# 用例生成约束（必须逐条遵守）

## A. 静态约束（测试原理）
1. **design_method（必须字段）**：每条用例**必须**标注采用的测试设计方法，取值只能是以下之一：
   等价类划分 / 边界值分析 / 判定表 / 状态迁移 / 场景法 / 错误推测。
2. **步骤可定位**：`target` 用「页面元素中文名 (种类=真实取值)」格式，种类取 `id` / `class` / `page` / `tab` / `text`：
   - **必须与注入的 UI 契约里该取值所属的种类一致** —— 契约会分别列出「可用 id 锚点」「可用 class 锚点」「页签」「导航页」；
     把页签键当元素 id 用（如 `(id=tools)`，而 `tools` 只是页签键）会被门禁拒绝。
   - 无 UI 契约时省略括号，只写中文元素名。
   - 动作必须取自系统注入的**动作清单**（每次生成时随「用例 JSON 字段约束」下发，
     按「操作用 / 断言用」分组并带一句话说明）。**按语义选词**，不要一律用 `check`：
     断言元素不可见用 `expectNotVisible`、按钮置灰用 `expectDisabled`、
     数量用 `expectCount`、激活/展开态用 `expectState`、上传用 `upload`。
   - **每条用例至少一个断言动作**（`expect*`）；`waitFor` 是同步等待，不算断言。
3. **预期可断言**：URL / 文本 / 状态 / 金额；金额给精确值（¥ 千分位、2 位小数，如 ¥4,727.05）。
   - `expected` 每条**必须超过 8 个字符**（不含标点计数），且写明**可观测对象**：
     具体页面/元素/字段/状态/数值。含具体数字的断言不受长度限制（如「数量 1→2」）。
   - 不合格示例（会被门禁拒绝）：`成功`、`正常`、`通过`、`无异常`、`页面渲染`、`跳转首页`。
   - 合格示例：`登录成功后跳转至首页`、`页面成功渲染并显示预期内容`、`删除后小计与合计金额均归零`、
     `导航栏显示当前用户昵称`、`数量 1→2 且小计同步更新`。
4. **testData 必须扁平**（最易把 JSON 写坏的地方）：
   - 只能是「键=值」字符串数组，如 `["phone=13800138000","password=123456"]`；
   - **值必须是标量**（数字 / 布尔 / 短文本）；**禁止嵌套对象或数组**——`{"tool":{"params":[{"name":"city"}]}}` 这类结构需要多层引号转义，实测会导致整轮输出作废（模型把全部预算耗在自我纠错上，正文一个字符都没写出来）；
   - 字符串值内**禁止出现 `"` 或 `\`**，需要引号用「」或『』；**禁止真实换行**，用「；」分隔；
   - `steps[].data` 同样只能是字符串；
   - 无法扁平表达的复杂数据写进 `preconditions` 的纯文本，不要放进 testData。
5. **反模式禁止**：
   - 模糊步骤（"随便点点"、"执行操作"）；
   - 不可验证预期（"表现正常"、"无异常"）；
   - 用例互相依赖 / 共享可变状态；
   - 重复用例（同步骤 + 同预期）；
   - 为凑数量生成的同质用例。
6. **标签口径**：全量带 `@regression`；按模块带模块标签（@auth/@cart/@checkout…）。
   **不要输出 `@smoke`** —— 它表示「部署后最先跑的最小集合」，由系统统一判定
   （P0 中每需求 1 条、排除边界与异常、总量 ≤ 20%），你标的会被覆盖。
7. **不输出思考过程**：禁止输出 `<think>` 之类的推理标签，直接输出最终 JSON；思考会占用输出预算，导致 JSON 被截断。
8. **输出前自检**：对照校验规则自查（id 格式 TC-<MOD>-<SEQ>、module/priority 枚举、requirement 为 REQ-*、steps/expected 非空、id 全局唯一、testData 全为「键=值」标量），再输出 JSON。
